## Project overview

Apex is a 3D printer slicer UI developed by Aelox Hardware: a Babylon.js viewport (build plate, printer boundary shader, model loading/manipulation) surrounded by shadcn/ui panels for file management, printer/filament config, texture editing, and slicing. This repo was originally scaffolded from the `vite_react_shadcn_ts` template — expect those scaffolding conventions (see AI_RULES.md) alongside hand-written slicer-specific code.

pnpm dev           # vite dev server on port 8080

## Architecture

### Global event bus, not shared state

There is no state management library and no shared React context between the sidebar/panel components and the 3D viewport. Instead, `Viewport3D.tsx` and every panel component communicate exclusively through `window.dispatchEvent(new CustomEvent(...))` / `window.addEventListener(...)`, using a fixed set of `apex-*` event names, e.g.:

- `apex-tool-changed` — Sidebar → Viewport3D (select/move/rotate/scale/delete tool switch)
- `apex-mesh-selected`, `apex-mesh-deleted` — Viewport3D → ModelStatusBox, SliceSidebar, SliceModal, TextureEditorModal
- `apex-model-hover` — Viewport3D → ModelHoverTooltip
- `apex-import-model` — Sidebar → Viewport3D; Viewport3D → ModelStatusBox/SliceSidebar
- `apex-camera-updated` — Viewport3D → ViewCube (camera orientation sync)
- `apex-set-camera-view`, `apex-set-camera-custom`, `apex-reset-camera`, `apex-fit-screen` — panels/ViewCube → Viewport3D
- `apex-axis-changed` — AxisSidebar → SliceModal
- `apex-request-textures`, `apex-textures-loaded` — TextureEditorModal ↔ Viewport3D
- `apex-set-tooltip`, `apex-reset-tooltip` — CustomTooltip → TopRightMenu

When adding a feature that needs to move data between the viewport and any panel, follow this pattern rather than introducing prop drilling, context, or a store. When adding a new event, grep for `apex-` across `src/components` first to check whether an existing event already carries the needed data.

### Viewport3D is a self-contained Babylon.js engine

`src/components/Viewport3D.tsx` owns the entire Babylon.js lifecycle in a single `useLayoutEffect`: engine/scene/camera creation, the printer build-volume boundary (custom GLSL shader material defined inline via `BABYLON.Effect.ShadersStore`, radius/height constants at the top of the file), mesh import (`babylonjs-loaders` for GLB/STL), gizmo-based move/rotate/scale tools, mesh picking/highlighting, and hover/selection broadcasting. It holds all Babylon state in refs (`engineRef`, `sceneRef`, `cameraRef`, `gizmoManagerRef`, `modelsRef`, `selectedMeshesRef`) rather than React state, since Babylon objects are mutable and not meant to trigger re-renders. React state is only used for the few bits that need to affect JSX (e.g. `selectedMeshName`).

Camera conventions (user's decisions, 2026-10-06): panning (middle button) is a **lens shift** added to the projection matrix (`camera.getProjectionMatrix` is wrapped), not a camera move, so objects are seen from the same angle whatever the translation; preset views and entering Modélisation reset it. Wheel zoom is toward the cursor; its step is a fixed distance (≈30 mm per notch) outside Modélisation and a percentage inside it.

### Component/style structure

- `src/pages/Index.tsx` is the single page and composes every top-level panel; routing lives in `src/App.tsx` (React Router, per AI_RULES.md keep routes there).
- Feature panels (`Sidebar`, `FileSidebar`, `CategoriesSidebar`, `PrinterConfigSidebar`, `SliceSidebar`, `SliceModal`, `TextureEditorModal`, `AxisSidebar`, `TopRightMenu`, `ViewCube`, `ModelStatusBox`, `ModelHoverTooltip`) each pair with a `*.module.scss` file for custom styling (glassmorphism panels, custom sliders/drag handles) — Tailwind is used for layout/spacing, SCSS modules for bespoke visual treatment that Tailwind utilities don't cover.
- `src/components/ui/*` is generated shadcn/ui code — per AI_RULES.md, don't edit these directly; wrap or compose new components instead.
- Path alias `@/*` maps to `src/*` (configured in both `vite.config.ts` and `tsconfig.json`); shadcn aliases (`@/components`, `@/lib`, `@/hooks`, `@/components/ui`) are defined in `components.json`.
- Toast notifications go through `src/utils/toast.ts` (`showSuccess`/`showError` wrapping `sonner`), not direct `sonner` calls.

Decided with the user in discussion. **Status: J0 (transport), J1 (C++ kernel), J2 (Electron bridge) and J3 (live deformation + Édition panel, 2026-10-02) done; next: writing the file + encrypted journal (user: "next step"), then J4 (integrated latency), J5 (packaging)** — plan in `C:\Users\test_\.claude\plans\peut-on-commencer-par-la-linked-elephant.md`. ### Mechanism
- The user places **handles** in the G-code preview, then translates or rotates them. The selected trajectory point and its neighbours follow, weighted by an **adjustable influence** (not "weak": adjustable).
- Neighbourhood is measured every possible way (3D radius, along the toolpath, per layer; mm, point count or layer count). **Every mode is individually toggleable and tunable.** Falloff profile selectable (linear / gaussian / cubic / plateau); anisotropic influence is a setting; an influence barrier at layer / line-type boundaries is an option.
- Multiple handles with merged influences; lockable points/zones; symmetry; copy/paste of a deformation between handles; handles bound to a spline.
- Rotating a handle must also rotate the **B orientation** of neighbouring points (rotation is not purely geometric on this machine). Extrusion **E** must be recomputed after deformation.
- Adjacent toolpaths either **stretch/compress** (when enabled) or are **trimmed** according to the deformation (stair-step first, then a re-pass over the twisted toolpath). Trimming creates new toolpath geometry — treat it as a **second phase** after plain deformation.

### Real-time requirement (the hard part)

The addon needs the `win_delay_load_hook.cpp` redirect of `node.exe` to the host executable.

### Undo and file handling
- Full undo/redo. Edits are stored as transformations (handle, delta, influence), not data copies.
- The file is **modified in place, original not kept**, except for an imported (not locally sliced) G-code, which only offers an **EXPORT COPY** button.
- The journal and the headers are **encrypted** with an Apex-specific scheme. The user's reason is publicity (a closed-looking feature on an open system gets talked about). **It is not a security boundary**: the project is open source, so any key is public — never describe it as protection.
- **Decisions of 2026-10-06** (detail and checks in `CDC_INTEGRATION_NOEUDS.md`, D2–D7). They **supersede** the earlier "journal written as G-code comments".
  - The **G-code headers are encrypted** and carry as much slicing metadata as possible. They include the Apex marker that tells a locally sliced file (edited in place) from an imported one (EXPORT COPY only). Commands stay plain.
  - **The G-code edit history goes only into the G-code's encrypted header** (not the 3MF, not an STL). The user can turn it off with a global setting, on by default; when off, nothing is written and undo is session-only.
    - Format: transformations + a fingerprint of the result, with as much data as possible; replay must be deterministic.
    - The rest of the project history (every other state-changing event) goes into a 3MF project file. The app has no 3MF support yet, so that is a new feature, independent of the G-code.
    - Undo after reopening: each entry also stores the before-values (R, C, Z, B, E) of the touched points, compressed, because the G-code is edited in place and the original is not kept.
  - **Encryption is multi-level**, in this order: Louis XIV's Great Cipher → AES → Vigenère → Fleissner grille → Enigma → AES. It covers the whole encrypted G-code header (metadata written by the engine in Python, plus the journal appended by the UI), with shared test vectors.
  - **Handle gestures**: drag = rotate the deformation and set the influence together; Ctrl + drag (⌘ on Mac) = rotation only; Alt + drag = influence only. They must be explained in the bottom-of-screen tooltip (`apex-set-tooltip`) on handle hover. Electron's auto-hidden menu bar must not pop up on Alt.
- **Implemented 2026-10-06 (D1, D2, D3, D6, tested end to end; detail in `CDC_INTEGRATION_NOEUDS.md`)**:
  - **D1, lock**: padlock droplet above the open node (reusable `Droplet`, same mitosis as "+"). Locked = red ring #ff2d55. Unlocked, dragging slides the node along the toolpath (picking under the cursor); locked, dragging deforms.
  - **D2, rotation**:
    - Shader formula `p' = pivot + R(w·angle)(p − pivot) + w·T`, with normals rotated too.
    - The axis faces the camera. The angle sign is measured at drag start by projecting a small test rotation.
    - Kernel conversion: axis y↔z swapped, angle negated.
    - A rotation is committed at the end of the handle drag (node locked only).
  - **D3, E**:
    - The kernel takes `e` (per-segment ΔE) at load, and `kValuesPerPoint = 5` (R C Z B E) everywhere.
    - E = e₀·(1 + factor·(len'·h'/len·h − 1)), clamped ≥ 0; an unknown height keeps a ratio of 1.
    - A commit also edits the points whose E alone changes (dependents and the first fixed point after moved matter).
    - The first layer's height is measured to the plate, so lifting it changes its E.
  - **D6, writing** (`src/utils/gcodeWriter.ts`):
    - Rewrites only `editedMoves` lines (4 decimals for positions, 5 for E), always from the ORIGINAL text, so `lineIndex` stays valid.
    - In absolute E mode, a `G92 E<original>` follows each run of edited lines, so the rest of the file is untouched.
    - In-place write is atomic (`apex:write-gcode`, temp file + rename, G-code extensions only).

- **Shape-preserving editing (user's decision, 2026-10-06): the object keeps its shape, only the layers' shape changes.** Kernel `InfluenceParams.keep_shape` (default on; off = plain weighted rigid motion, used by the mechanism tests):
  - first layer (on the plate) and free surface (nothing rests on it) are fixed and refused as node points; weights fade towards them by depth in the contact graph;
  - shell toolpaths (no matter on one side within their layer, detected lazily by the kernel) slide on their wall (normal component removed, tangent plane);
  - layer thickness stays within 0.06–0.3 mm (`KernelParams.min/max_layer_mm`, printer profile later; tolerance 0.005 mm for layers already at a bound). The requested translation is braked: speed ratio 1 − x/x_lim, applied = s(1 − e^(−1/s))·T (`brake_factor`), 0 at the limit;
  - along the stack (`drag_direction` within ~73° of the node's head axis), weights grow with the **thickness slack** of the layers crossed, measured from the plate/top or the edge of the recommended reach, and every point moves along its own head axis by w·τ (bent layers stay consistent); the lateral part moves only the interior. The kernel reports `rebuild` when the drag flips direction;
  - handle length = **recommended** reach. **Influence mode** (Influence section of the panel, `reachMode`, user's decision 2026-10-07): **Auto** (default): handles stay out but turn violet, snap to their default spread (`HANDLE_REST_PX`) and only their orientation can change (still rotates the deformation; no lock, no deletion by drag; their Portée length/lock is kept for later); the reach starts from `spatial.radius_mm` (handle directions/anchors ignored) and widens it (×1.25–2 per step) while the limit blocks, up to the whole object, and brakes only when no new points are gained and the reach already covers the object's diagonal; reset after commit or mode change. **Portée**: handles fully adjustable again, never exceeds their reach, the node brakes at the limit;
  - shader attributes `apexEditWeight`, `apexEditSlide` (wall normal), `apexEditAxis` (head axis) + uniform `apexEditStackAxis` reproduce the kernel formula exactly; the node is drawn at the kernel's dragged tip.
  - Pitfall found on the elbow: a uniform translation projected onto slightly different wall planes, or a 3D falloff along the stack, changes the thickness of layers already at a bound and freezes everything; hence slack-based weights and per-point axes.
- **Freedom beyond the layer-thickness limit (user request 2026-10-07)**: stretch/compress along the stack used to be capped by the sum of the thickness slacks of the layers in reach (each layer absorbs only `max − h` or `h − min`; ±0.1 mm per 0.2 mm layer). The slack-proportional weights were already optimal (all layers hit their bound together), so the real levers are the bounds and the topology:
  - **Capacity** (`EditKernel::capacity_mm`, `setHandle` → `capacityMm`): axial displacement the layers in reach can absorb = `min(slack_plate, slack_top)` of the node; panel shows "capacité X mm · demandé Y mm" (red when exceeded). Auto reach still widens from the drag brake (`limitScale`).
  - **Editable bounds** (`utils/layerLimits.ts`, localStorage, panel section "Épaisseur de couche"): min, max and **variable width** factor f (1 = off). `KernelParams::width_factor`, `min_layer_floor() = min/f`, `set_layer_limits` (op `setLayerLimits`, no reload, redo `setHandle` after). Variable width: a bead below `min` widens (max f×) so E uses the section `min(f·h, min)` (`extrusion_height`, `e_height_ratio`); above `min` E is unchanged.
  - **Re-slicing = interpolated layers (`InfluenceParams.reslice`, default on; ignored with trimming or without keep_shape)**. During the drag the max bound brakes only at `(reslice_max_layers+1)·max` (default 4 extra layers). `compute_layer_counts` (per drag frame, over affected + dependents): n = ceil(h/max) − 1 for points more than `max(0.015, 5 %·max)` over the max, runs of ≥ 2 consecutive points of one pass share the largest n and must be ≥ `reslice_min_run_mm` (2 mm) long or > 1.5×max thick. E of the original beads uses h/(n+1). At **commit** `build_reslice_plan` returns, per run, the points to insert BEFORE the run's first point: lift of the previous point (along the head axis, `lift_mm` 1), then for each layer j = 1..n (bottom first) lift / approach (no deposit) / the run's points at fraction j/(n+1) between the lowest support and the point (deposit, E recomputed) / lift, then lift + duplicate of the previous point so the original segment q(a−1)→q(a) keeps its deposit. Tests `test_reslice` (mutation-checked on the fraction), `test_capacity_and_width`.
  - **Insertion in place (2026-10-07, replaces the first "rewrite + reload" version)**. The kernel owns the topology: `insert_blocks` / `remove_blocks` splice its base arrays (`init_derived` rebuilds geometry, passes, grid, supports, depths; ~0.35 s per 1 M points) and keep `locked_`/types. A commit with a plan yields a `HistoryEntry` with `inserted` blocks (`InsertBlock{at,values,extruding}`, `at` = index in the state WITH the blocks) and its `indices`/`trimmed` already in that indexing; older entries stay in their own indexing because history is consumed LIFO (undo removes the blocks first). `change.splice = {inserted, blocks}`; `change.indices` are always in the state with blocks: **insert before applying values (commit, redo), apply values before removing (undo)**. Redo/undo are exact (test compares R C Z B E bit for bit). Addon: `setTimes`/`setTypes` must be re-sent after a splice (inserted points copy the host's type; times are cleared).
  - UI side: `utils/gcodeSplice.ts` (`insertMoves`/`removeMoves`/`remapMoveIndex`) splices every per-move array of `ParsedGCode` (moves, speed, accel, temps, fan, layer data, E data, markers, offPlate, edited/trimmed sets, times) with host values; inserted moves have `lineIndex = INSERTED_LINE` and are listed in `parsed.insertedBlocks`. `gcodeLayer.replaceMoves(parsed)` rebuilds the meshes while the old ones stay visible until the new ones are ready (flags/weights cleared: they used the old numbering). `gcodeEditController.applySplice` remaps nodes, splices, re-sends times/types and refreshes locks/validation. **No file rewrite, no reparse, no snapshots**: the writer (`writeEditedGCode`) writes `insertedBlocks` at save time before the line of the original move that follows them (command/F/type comment copied from it; absolute E closed by `G92 E<eAbsBefore of that move>`; a G92 after an edited run now targets the next ORIGINAL move). **The journal is not written while `insertedBlocks` is non-empty** (its indices describe the pre-splice numbering) and the journal arrays are emptied at each splice.

### Versioning (user's decision, 2026-10-08)
**Single version number in the shared repository (user's decision, 2026-10-26).** The Apex application (engine + interface) has **one** version number, kept in the shared repository **`aeloxhardware/apex`**: `VERSION` (source of truth) and `VERSIONS.md` (log). It changes with every version of the engine **and** of the interface. **On every version change made here**, also update `VERSION` and `VERSIONS.md` in `apex` (pull its latest state first: the engine may have changed the number in the meantime), and keep `apexVersion` in `package.json` equal to `apex/VERSION`. `RELEASES.md` below keeps the detail of the interface's changes. Format, levels and conflict rule: `apex/integration/RULES.md`, §9 (same scheme as below, now applied to the whole application). Engine and interface are developed separately, one session per repository: `apex/integration/RULES.md` (rules and contract) and `apex/integration/REQUESTS.md` (open requests, read at session start).

Format `<préversion>-<public>.<global>.<majeur>.<moyen>.<mineur>.<add-ins>.<correctif>.<builds>`, e.g. `alpha-0.2.1.2.1.1.1.221`. Single source: `apexVersion` in `package.json` (injected as `__APEX_VERSION__` by Vite, shown on the splash and the preview notice). `version` (semver, required by npm/electron-builder) = `<public>.<global>.<majeur>`, here `0.2.1`: keep it in sync.
- **Préversion letter** (`alpha`, then beta…): maturity.
- **Public**: public release number of the software, 0 while in pre-release.
- **Global**: refactor of the whole software. 0 = initial version (never seen by Claude), 1 = LiquidGlass v1 without workspaces, 2 = the current one.
- **Majeur**: new workspace, new engine, important new feature. 1 = the new Édition mode of the Prévisualisation space.
- **Moyen**: fairly important new features. Currently 2: LiquidGlass splash screen and LiquidGlass bottom-of-screen tooltip.
- **Mineur**: noteworthy new feature, e.g. choosing whether handles influence nodes.
- **Add-ins**: a button, a small thing. Counting rule not settled (1 by default): count as it goes.
- **Correctif**: fix of a bug in an existing feature (1 by default).
- **Builds**: total builds since the last *compiled version made public* (e.g. the last working GitHub Release, not the last commit), up to the current one; every app launch counts, even for a trivial fix (221 by default).
- Bumping a level: the levels to its right restart (Builds excepted: it only restarts at a new public compiled version). Not yet defined: reset values to the right (0 or 1) — ask if it comes up.
- **`RELEASES.md`** (repo root) tracks the history of every software version (by version number; NOT a mirror of GitHub Releases, which only matter for the Builds counter) and states the current one. Update it with every version change, in the same commit.
- **Version as finely as possible: at every change made**, not only at releases. Each change bumps the right level (Add-ins for a button/small thing, Correctif for a bug fix, Mineur/Moyen/Majeur/Global above), updates `apexVersion` (+ `version` in `package.json`) and `RELEASES.md`. Builds counts every build/launch since the last compiled version made public.
- **Every version must appear in the commits**: a commit that changes `apexVersion` starts its message with the full version (`alpha-0.2.1.2.1.1.1.221 : …`), and each release build comes from a commit tagged with it (`git tag <version>`).
